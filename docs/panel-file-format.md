# Panel file format

The JSON file produced by **File → Export JSON** and read by **File → Import JSON**. It is meant to
be read, hand-edited, and generated by tools, so this page is the complete specification.

The current version is **5**. A file with any other `version` is refused outright.

## Example

```json
{
  "version": 5,
  "name": "Lusco House",
  "rooms": ["Family", "Kitchen", "Garage"],
  "breakers": {
    "1": { "breaker": "single", "circuits": [{ "room": "Family", "label": "Lights" }] },
    "2": { "breaker": "tandem", "circuits": [{ "room": "Family", "label": "Plugs" }, { "room": "Kitchen", "label": "Disposal" }] },
    "3": { "breaker": "240+2x120", "circuits": [{ "label": "Bath" }, { "room": "Kitchen", "label": "Range" }, {}] },
    "6": { "breaker": "quad" },
    "12": { "breaker": "double", "circuits": [{ "room": "Garage", "label": "EV charger" }] }
  },
  "staging": [
    { "breaker": "quad", "circuits": [{ "room": "Garage", "label": "Freezer" }, {}, {}, {}] },
    { "breaker": "single" }
  ]
}
```

The smallest valid file:

```json
{ "version": 5, "breakers": {} }
```

## Top level

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `version` | number | **yes** | Must be exactly `5`. Anything else is refused. |
| `name` | string | no | The panel's name. Any string, including `""`. Defaults to `"Main Panel"` if absent or not a string. |
| `rooms` | string[] | no | The room list. **Order matters** — it fixes each room's colour in the app and in the exported image. |
| `breakers` | object | **yes** | Keyed by slot number. Refused if absent, `null`, or an array. |
| `staging` | array | no | Breakers set aside, not in the panel. See [Staging](#staging). Omitted when empty. |

`rooms` is optional even when circuits name rooms: any room named on a circuit is added automatically
if it is missing. Listing rooms explicitly is still worthwhile because it fixes their colour order
and lets you carry rooms that no circuit uses yet.

Room names are trimmed; blanks and duplicates are ignored. At most 192 rooms are kept (one per
circuit on a full panel).

## Breakers

`breakers` is an object whose **keys are slot numbers as decimal strings** and whose values describe
one breaker each.

```json
"breakers": {
  "3": { "breaker": "240+2x120", "circuits": [ ... ] }
}
```

- A key must be a plain decimal integer string: `"1"`, `"12"`, `"48"`.
  `"01"`, `"1.0"`, `"0x3"`, `"1e1"`, `" 2"` and `"+3"` are **rejected**, because they are distinct
  JSON keys that would silently collapse onto the same slot.
- A breaker that occupies two slots is listed **once**, under its topmost slot. The breaker at
  `"3"` above also occupies slot 5; there is no `"5"` entry.

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `breaker` | string | **yes** | One of the names in the table below. |
| `circuits` | array | no | One entry per throw. Shorter arrays are padded with blanks, longer ones truncated. Omit entirely when nothing is labelled. |

### Breaker names

| `breaker` | Slots | Poles | Circuits, in array order (top to bottom) |
| --- | --- | --- | --- |
| `single` | 1 | 1 | 120V |
| `tandem` | 1 | 2 | 120V, 120V |
| `double` | 2 | 2 | 240V |
| `2x120` | 2 | 2 | 120V, 120V |
| `2x240` | 2 | 4 | 240V, 240V |
| `240+2x120` | 2 | 4 | 120V, **240V**, 120V |
| `quad` | 2 | 4 | 120V, 120V, 120V, 120V |

The array order is the order the breaker face draws the throws. Note that `240+2x120` puts its
**240V circuit in the middle**, at index 1 — not first.

### Circuits

Each entry is an object with two optional string fields:

| Field | Type | Notes |
| --- | --- | --- |
| `room` | string | Which room the circuit serves. Trimmed. Max 200 characters. |
| `label` | string | What it feeds. Not trimmed. Max 200 characters. |

Both are optional and an empty one may be left out entirely, so `{}` is a valid unlabelled circuit
and is how the exporter writes a gap:

```json
"3": { "breaker": "240+2x120", "circuits": [{}, { "label": "Range" }, {}] }
```

When **every** circuit on a breaker is blank, omit `circuits` altogether:

```json
"6": { "breaker": "quad" }
```

## Staging

Staging holds breakers that exist in the plan but are not in the panel — the app puts them there
when you drag one off a slot to make room, and they keep every label while they wait.

It is a **list, not a map**, because a staged breaker has no slot to key it by. Each entry is the
same object a `breakers` value is, minus any notion of position:

```json
"staging": [
  { "breaker": "quad", "circuits": [{ "room": "Garage", "label": "Freezer" }, {}, {}, {}] },
  { "breaker": "single" }
]
```

- Order is preserved; it is the order the app shows them in.
- Staged breakers occupy **no slots**, so they never collide with anything and never make a
  `breakers` entry invalid. The only thing that can be wrong with one is its `breaker` name.
- They are not counted in the panel's circuit, monitoring or slot totals — they are not installed,
  and they do not appear in the app's PNG/SVG export, which pictures the panel as built.
- Omit the key entirely when nothing is staged. `"staging": []` means the same thing.

Generating a file with no `staging` key is always valid; it simply lands with staging empty.

## Slot numbering

The panel has **48 slots in two columns**. Slots alternate across the face: **odd numbers run down
the left column, even numbers down the right**, so row *r* holds slots `2r-1` and `2r`.

```
row 1:   1 │  2
row 2:   3 │  4
row 3:   5 │  6
   …
row 24: 47 │ 48
```

A two-slot breaker occupies slot **N and N+2** — the next row in the *same* column, which is how it
straddles both bus legs. It therefore has the same parity in both slots, and:

- A one-slot breaker (`single`, `tandem`) may start at any slot **1–48**.
- A two-slot breaker (everything else) may start at **1–46**, never 47 or 48, since it would need a
  slot 49 or 50 that does not exist.
- Two breakers may not share a slot. A `double` at 3 occupies 3 and 5, so nothing else may claim 5.

## What gets refused, and what gets skipped

**The whole file is refused** — nothing in the app changes — when it is not valid JSON, is not a
JSON object, has a `version` other than 5, or has no usable `breakers` object.

**Individual entries are skipped and counted**, with the count reported to the user, when:

- the `breaker` name is not one of the seven above,
- the slot key is not a plain decimal integer,
- the slot is outside 1–48,
- a two-slot breaker starts at 47 or 48,
- the entry overlaps a breaker already placed — the **lower slot number wins**, the later one is
  skipped,
- the entry's value is not an object,
- the file holds more than 500 breaker entries; the rest are skipped,
- a `staging` entry is not an object, or names a breaker that is not one of the seven,
- `staging` holds more than 48 entries; the rest are skipped.

A `staging` value that is not an array is treated as absent rather than counted as a skip — there is
no way to tell how many entries it was meant to hold.

Anything else malformed is coerced rather than rejected: a non-string `name` falls back to the
default, non-string rooms are ignored, a `circuits` value that is not an array is treated as absent,
and a circuit entry that is not an object becomes a blank circuit.

## Limits

| Limit | Value |
| --- | --- |
| Slots | 48 |
| Breakers | 48 (one per slot; fewer if any are two-slot) |
| Breaker entries read from a file | 500 |
| Staged breakers | 48 |
| Circuits per breaker | 4 |
| Rooms | 192 |
| `room` / `label` length | 200 characters |

## Generating a file

The minimum a generator must get right:

1. `version` is `5` and `breakers` is present.
2. Slot keys are plain decimal strings within 1–48.
3. Two-slot breakers are listed once, under the topmost slot, and leave `slot + 2` free.
4. `circuits` is in the arrangement's throw order — remember `240+2x120` is 120V, **240V**, 120V.

Everything else is optional. `rooms`, `name`, `staging`, `circuits` and the individual `room` /
`label` fields can all be omitted.

### JSON Schema

Describes what to generate. The importer is more lenient than this — it ignores unknown fields
rather than failing — but a file matching this schema will always import cleanly.

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "Breaker Panel Builder panel file",
  "type": "object",
  "required": ["version", "breakers"],
  "properties": {
    "version": { "const": 5 },
    "name": { "type": "string" },
    "rooms": { "type": "array", "items": { "type": "string", "maxLength": 200 }, "maxItems": 192 },
    "breakers": {
      "type": "object",
      "propertyNames": { "pattern": "^(?:[1-9]|[1-3][0-9]|4[0-8])$" },
      "additionalProperties": { "$ref": "#/definitions/breaker" }
    },
    "staging": {
      "type": "array",
      "maxItems": 48,
      "items": { "$ref": "#/definitions/breaker" }
    }
  },
  "definitions": {
    "breaker": {
      "type": "object",
      "required": ["breaker"],
      "properties": {
        "breaker": {
          "enum": ["single", "tandem", "double", "2x120", "2x240", "240+2x120", "quad"]
        },
        "circuits": {
          "type": "array",
          "maxItems": 4,
          "items": {
            "type": "object",
            "properties": {
              "room": { "type": "string", "maxLength": 200 },
              "label": { "type": "string", "maxLength": 200 }
            },
            "additionalProperties": false
          }
        }
      },
      "additionalProperties": false
    }
  }
}
```

## What the file does not carry

Shrinking a breaker's throw count hides the extra circuits rather than deleting them, so their
labels come back if you switch the arrangement out again. **Those hidden labels are not exported** —
the file records only the circuits the arrangement currently shows.

Nothing derived is stored either: circuit counts, voltages and which circuits keep their own
monitoring channel are all computed from `breaker`, so a file cannot contradict itself about them.

## Monitoring, for context

A smart panel meters per slot, so a circuit keeps its own monitoring channel exactly when every slot
its breaker sits in carries one pole — that is, when poles equal slots. `single`, `double` and
`2x120` qualify; `tandem` and every four-pole arrangement do not. A generator does not need to
encode this; the app derives it.
